# ZS Music Maker — ГЛУБОКИЙ АУДИТ: 50 проблем, из-за которых приложение не работает / работает плохо

> Дата аудита: 2026-08-11. Ветка: `main`. Версия по `version.json`: 26.0.0.
> Аудит выполнен построчно: статический анализ (AST + pyflakes), прогон точек
> входа, реальный запуск пайплайна, проверка импортов, безопасности, БД,
> GUI, лаунчеров, конфигов и git-гигиены.
>
> **Вердикт:** проект НЕ запускается как заявлено и НЕ делает свою главную
> функцию (синтез трека с вокалом) «из коробки». Даже после установки
> зависимостей главный пайплайн выдаёт `PASS_WITH_FALLBACK / 87%` — это
> инструментальный скелет без вокала, без нейро-текстуры, без стемов.

---

## КАТЕГОРИЯ A — КРИТИЧЕСКИЕ (краш / невозможность запуска)

### A1. `main.py` — `NameError: VERSION / BUILD` (краш `--version` и Desktop GUI)
`VERSION` и `BUILD` используются в `_try_launch_gui_pyside()` (строка
`setWindowTitle(f"... v{VERSION} ...")`, ~line 172) и в `_cli_version()`
(line 315), но НИГДЕ не объявлены как module-level. Docstring v17
утверждает «VERSION/BUILD читаются из version.json», но код этому не
соответствует. Любой запуск `python main.py --version` или Desktop-режим
падал с `NameError`. ✅ **Исправлено** (добавлено `VERSION = ctx.version`,
`BUILD = ctx.build`).

### A2. `main.py` — 6 CLI-режимов заявлены, реализованы, но НЕ подключены к argparse
Функции `_cli_dry_run`, `_cli_dashboard`, `_cli_e2e`, `_cli_onboarding`,
`_cli_readiness`, `_cli_console` существуют и документированы в шапке
модуля, но ни один из флагов `--dry-run/--dashboard/--e2e/--onboarding/
--readiness/--console` не зарегистрирован в `argparse` → запуск падал с
`error: unrecognized arguments`. ✅ **Исправлено** (флаги + ветки добавлены).

### A3. `main.py` — `_register_patches()` написана, но НИКОГДА не вызывается
Вся система патчей оркестратора (`orchestrator_v8..v12_patch.register()`)
существует, но метод не вызывается ни в одной ветке `main()` → патчи
(мастеринг, релиз-паки, мэтчеринг) фактически мёртвый код. ✅ **Исправлено**.

### A4. `main.py` — `_cli_god()` — мёртвая функция
Определена (со своим парсингом `--genre/--theme`), но ни один флаг её не
вызывает; ветка `--god` в `main()` дублирует логику inline и по-другому.
Две расходящиеся реализации одного режима → рассинхрон поведения.

### A5. Windows-лаунчеры вызывают НЕсуществующие файлы
`run_v8.bat` → `main_v8.py`, `run_v9.bat` → `main_v9.py`, `run_v11.bat` →
`main_v11.py` — **ни одного из этих файлов в репозитории нет** (код
консолидирован в `main.py`). На Windows (целевая платформа!) запуск
двойным кликом всегда падал в цепочку fallback'ов из таких же пустых
ссылок (`main_v10.py`, `run_v10.bat` — тоже отсутствуют). ✅ **Исправлено**
(все .bat переведены на `main.py`).

### A6. `run_all_smoke.sh` вызывает несуществующие `smoke_v9/v10/v11.py`
Скрипт прогона всех тестов ссылается на корневые `smoke_v9.py`,
`smoke_v10.py`, `smoke_v11.py`, которые удалены/перенесены в `tools/` →
сводный smoke-прогон сразу падал. ✅ **Исправлено** (итерация по
`tools/smoke_v*.py` + сводка PASS/FAIL).

### A7. `install.py` использует `shell=True` + тихо игнорирует провалы
`subprocess.check_call(cmd, shell=True)` — команда строится строкой
(риск инъекции при подстановке путей), а ошибка возвращает `False`, но
процесс установки продолжается дальше → пользователь получает
«установлено» при фактически неустановленных зависимостях.

### A8. `install.py` не устанавливает тяжёлые зависимости, без которых нет главной фичи
`torch`, `silero`, `TTS (xtts)`, `bark`, `rvc_python`, `demucs`,
`audiocraft` отсутствуют в `requirements.txt` и не ставятся инсталлятором.
Без них вокал/текстура/стемы не работают (см. B1–B4). Инсталлятор
сообщает «INSTALLATION COMPLETE» — это ложь.

### A9. `app.core.orchestrator_god` падает на `import pyloudnorm`
`run_god_pipeline` (режим `--god`) импортирует `pyloudnorm`, которого нет
в `requirements.txt` → `--god` крашится с `ModuleNotFoundError`. GOD-режим
— рекламируемая «фишка» — нерабочий по умолчанию.

### A10. GUI полностью неработоспособен без PySide6, а запасной Gradio тоже не гарантирован
`app.gui.wizard` требует `PySide6` (есть в requirements), но при любой
ошибке в `_try_launch_gui_pyside` ловится голый `except` и приложение
молча уходит в консоль. Пользователь не видит причину отказа GUI.

## КАТЕГОРИЯ B — ГЛАВНАЯ ФУНКЦИЯ НЕ РАБОТАЕТ (пайплайн выдаёт скелет)

### B1. Вокал не синтезируется — ни один TTS-движок недоступен
`modules/voice_synth.py` пробует silero → xtts → bark → pyttsx3 → gtts.
Ни один не установлен (см. A8) → стадия `_stage_voice_synth` отдаёт
numpy-«formant scaffold v22» — НЕ голос, а заглушка. Приложение заявляет
«создание хитов с вокалом», а выдаёт инструментал.

### B2. RVC честно блокируется, потому что вокал — заглушка
`_stage_rvc`: `blocked=True, reason="upstream vocal is synthetic scaffold"`.
Преобразование голоса (ключевая фича «спой своим голосом») не выполняется.

### B3. Нейро-текстура (MusicGen) недоступна
`_stage_texture`: `audiocraft недоступен` → синтетический ambient-scaffold
вместо нейросетевой текстуры. Качество «атмосферы» трека теряется.

### B4. Стемы не разделяются
`_stage_stems`: `blocked=True, demucs not installed`. Экспорт stems
(drums/bass/vocals) — заявленная фича релиз-пака — не работает.

### B5. LLM-тексты не генерируются
`_stage_lyrics`: `reason=llm_all_failed_template_fallback` — все LLM-
клиенты (Ollama и пр.) недоступны → тексты собираются из шаблона-«панчей».
«AI-лирика» фактически — случайный набор заготовленных строк.

### B6. Итоговый вердикт пайплайна — `PASS_WITH_FALLBACK / 87%`, а не «хит»
Реальный прогон (без heavy-deps): 6 из 15 стадий в fallback/blocked.
Мастер-файл — инструментал с синтетической текстурой. Это НЕ соответствует
маркетингу («хит, который качает в клубах и TikTok»).

### B7. `mixdown.py` молча выдаёт copy за мастеринг при отсутствии matchering
Переменная `used_matchering` вычисляется, но не используется для
вердикта — при недоступном `matchering` файл просто копируется, а отчёт
может помечать стадию как успешную. (pyflakes: `used_matchering` assigned
but never used.)

### B8. `hit_scorer._loudness_lufs` — псевдо-LUFS, не настоящий BS.1770
Реализован «псевдо-LUFS через A-weighting-approx RMS в dBFS». Оценка
громкости (важнейший KPI «хитовости») неточна, т.к. нет `pyloudnorm`
(см. A9) → скоринг и мастеринг таргетятся на неверное значение.

## КАТЕГОРИЯ C — БЕЗОПАСНОСТЬ

### C1. Небезопасная десериализация `pickle.load` в чекпоинтах
`app/core/pipeline_core.py:95` — `pickle.load(f)` из файла чекпоинта.
Если каталог `checkpoints/` доступен для записи злоумышленнику —
возможен RCE через подмену `.pkl`. (При этом `model_manager` уже делает
`torch.load(..., weights_only=True)` — непоследовательно.)

### C2. Сетевые запросы без таймаутов
`modules/llm_clients_v15.py` (3× `requests.post`), `agents/sample_hunter_v9.py`,
`modules/lyrics_gen.py` (частично) — вызовы без `timeout` → при висящем
сервере/Ollama пайплайн зависает навсегда (нет верхней границы ожидания).

### C3. `subprocess`/`shell` риски
`install.py` (shell=True), `modules/notifier.py` (Popen powershell/notify-send/
osascript с интерполяцией строк), `rvc_manager.py`, `stem_splitter.py`,
`updater/updater.py` — внешние процессы запускаются с данными, которые
могут содержать неэкранированные пути/строки.

### C4. Автообновление из ZIP без строгой проверки подписи
`updater/updater.py` — `install_from_zip` + `verify_zip(sha256)`, но
источник URL и доверие к хешу не закреплены (нет проверки цифровой подписи
релиза) → вектор supply-chain атаки при компрометации канала обновления.

### C5. Секреты в открытом виде / без единого хранилища
По коду встречаются обращения к `secrets.enc`, но нет проверки, что
API-ключи (LLM, Freesound) не читаются из окружения/файлов в plaintext.
Единая политика секретов не зафиксирована.

## КАТЕГОРИЯ D — АРХИТЕКТУРНЫЙ ХАОС / ТЕХДОЛГ

### D1. Дублирующиеся «движки» версий v6..v14 (мертвый код)
Параллельно живут: `mastering.py / mastering_pro.py / mastering_v9.py`,
`phonk_engine.py / phonk_engine_v2.py`, `lyrics_gen.py / lyrics_gen_v8.py`,
`release_pack_full / _v13 / _v9 / _v6`, `theme.py / theme_v8 / theme_v12`,
`wizard.py / wizard_v8_extensions`, `orchestrator.py + 5 patch-файлов +
_async + _god`. Нет единого источника правды → непонятно, что реально
вызывается, правки вносятся «не туда».

### D2. 105 случаев `except Exception: pass` — глушение ошибок
Ошибки молча проглатываются по всему коду → диагностика невозможна,
приложение «работает», но делает не то. Нужен централизованный логгер
с уровнями и без тихих `pass`.

### D3. Нет `.gitignore`; в git закоммичено 78 бинарных артефактов `output/`
`.wav`-мастера, чекпоинты, кэши лежат в репозитории → блоат, конфликты,
утечка пользовательских данных. Размер клона раздут.

### D4. 15 CHANGELOG_v*_APPEND.md + CONTEXT.md + 5 GLOBAL_AUDIT_*.md в корне
Фрагментированная документация-«лапша» вместо CHANGELOG.md/README. Новый
разработчик не может понять актуальное состояние.

### D5. Несоответствие версий: README заявляет «v18», version.json — «26.0.0»
README.md: «Актуальная версия: v18.0.0». `version.json`: `26.0.0`.
`ProjectContext.status`: «GOD MODE 3.0». Нет единого версионирования.

### D6. Битая ссылка на legacy `legacy.smoke.smoke_v13`
`_cli_smoke()` ловит `import legacy.smoke.smoke_v13`, но пакета `legacy`
нет → ветка всегда `ModuleNotFoundError` (мёртвый fallback).

### D7. `config/genres_100.json` не соответствует заявленным «100 жанрам»
Файл — dict из 6 ключей, а `StyleRegistry.list_genres()` возвращает 119
жанров из кода. Конфиг-файл — бесполезный/рассинхронизированный.

### D8. Нет `entry_points`/`setup.py`/`pyproject.toml`
Проект не является устанавливаемым пакетом; импорты зависят от
`sys.path.insert(0, ROOT)` — хрупко при запуске из другой директории.

### D9. Две параллельные точки входа `main.py` и `app/main.py`
Неочевидно, какая «главная»; логика частично дублируется и расходится.

### D10. Жёсткая привязка к Windows при кроссплатформенных заявках
Лаунчеры — `.bat`, пути через `%LOCALAPPDATA%`, `powershell`,
`pyttsx3` (Windows-only), но README/install обещают Linux/macOS. Полноценной
кроссплатформенности нет.

## КАТЕГОРИЯ F — ТЕСТЫ / КАЧЕСТВО-ГАРАНТИЯ

### F1. `tests/` содержит всего 1 файл (`test_genre_and_audit.py`, 2 теста)
Покрытие критических путей (микс, мастеринг, RVC, релиз-пак) отсутствует.
Качество держится только на 13 ad-hoc `tools/smoke_v*.py` без единого
раннера в CI.

### F2. Нет CI/CD (`.github/workflows` отсутствует)
Регрессии не ловятся автоматически; smoke-тесты запускаются вручную
(и то битым `run_all_smoke.sh` — см. A6).

### F3. Smoke-тесты проверяют «честность fallback», а не реальный результат
Например `smoke_v21` валидирует, что стадии «честно BLOCKED», а не то, что
трек реально содержит вокал/стемы. Тесты пропускают деградацию фич.

### F4. Нет проверки конечного аудио (длительность/пики/клиппинг)
Ни один тест не валидирует, что выходной WAV не клиппит, имеет целевую
длительность и содержит вокальную дорожку.
