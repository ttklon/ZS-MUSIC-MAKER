# ZS Music Maker — приложение на Electron

Окно приложения — Electron. Оно не запускает Python-сервер и не ходит в сеть:
данные читаются из файлов проекта, тяжёлые операции запускаются той же
командой, что и в терминале (`python main.py …`), а вывод показывается
построчно.

```
desktop/
├── electron/
│   ├── main.js           главный процесс: запуск, IPC, меню, --smoke
│   ├── startup.js        замок единственного экземпляра, AppUserModelId
│   ├── window.js         окно: показ, ссылки, падение, размер, панель задач
│   ├── window-policy.js  решения об окне: размеры, фокус, прогресс, крах
│   ├── app-menu.js       меню приложения и текст «О приложении»
│   ├── app-paths.js      каталог «Музыка» и запасной путь
│   ├── ipc-project.js    каналы данных проекта (версия, жанры, готовность…)
│   ├── runtime.js        где лежит проект и есть ли Python (репозиторий или установка)
│   ├── pipeline.js       «Собрать бит»: один код для Electron, предпросмотра и потока
│   ├── render-host.js    рендер в worker_threads с откатом в главный процесс
│   ├── render-worker.js  точка входа потока рендера (вне app.asar)
│   ├── beat-service.js   IPC бита: рендер, банк, сохранение WAV и отчёта
│   ├── settings.js       settings.json в каталоге пользователя
│   ├── writable-data.js  куда писать досье (Program Files только для чтения)
│   ├── native-tasks.js   задачи «Запуска» без Python: файлы, готовность, досье
│   ├── preload.js        единственный мост к системе (contextIsolation)
│   └── tasks.js          белый список задач + запуск процессов
├── build/
│   ├── icon.png          иконка 1024×1024 (исходник)
│   └── icon.ico          иконка Windows (16…256)
├── src/
│   ├── index.html        разметка (CSP: без inline-скриптов и без сети)
│   ├── styles.css        оформление
│   ├── app.js            состояние, помощники, навигация
│   ├── sections/         разделы окна: overview, genres, beat, dossiers, tracks, run, health, help
│   └── core/
│       ├── fs-node.js  файловое API с ошибками вместо исключений
│       ├── catalog.js  жанры, пресеты, разбор inventory
│       ├── readiness.js расчёт готовности (сверен с Python)
│       ├── project.js  «модель проекта» для окна
│       ├── beat-options.js  границы рендера бита и параметров вокала
│       ├── dossier-edit.js  досье: список, создание и удаление без Python
│       ├── dossier-tracks.js треки досье в формате Python-менеджера
│       └── audio/      движок бита на JavaScript (порт modules/beat)
│           ├── rng.js          mulberry32: seed → одинаковый трек
│           ├── dsp.js          фильтры Баттерворта (сверены со scipy), огибающие
│           ├── instruments.js  синтез kick/snare/clap/hat/808/impact
│           ├── pattern-data.js ритм и акценты (сгенерировано из Python)
│           ├── patterns.js     жанр → семейство, velocity-карты
│           ├── humanize.js     микротайминг и «человечная» громкость
│           ├── variation.js    вариативность такта (пропуски, ghost-ноты)
│           ├── harmony.js      аккорды, голосоведение, пэд, стабы
│           ├── voices.js       голоса: ударные, бас, суб, гармония, FX
│           ├── tuning.js       частоты тоники, мажор/минор
│           ├── hook.js         мотив хука и его лид
│           ├── bar.js          один такт: слои, velocity, ghost-ноты
│           ├── master.js       уровни, дроп, ширина, дрейф, шум, лимитер
│           ├── vocal.js        формантный синтез вокала: слоги, мелодия
│           ├── takes.js        дубли: файл, синтез, тестовый (имитация входа)
│           ├── vocal-mix.js    как дубль попадает в микс и в отчёт
│           ├── arrangement.js  драматургия: секции, энергия, слои
│           ├── engine.js       рендер трека: план, секции по шагам, отчёт
│           ├── analysis.js     замеры «формульности» и «человечности» микса
│           ├── wav.js          запись WAV (PCM 16 / float32)
│           ├── wav-decode.js   чтение WAV: PCM 8/16/24/32 и float
│           └── bank.js         сэмпловый банк: манифест, лицензии, round-robin
├── scripts/
│   └── snapshot-readiness.js  снимок чисел через штатный Python-инструмент
└── test/             351 тест на `node --test`, без графической среды
```

## Запуск

Готовый установщик лежит в **релизе** и не требует входа в GitHub:

- страница со всеми сборками: <https://github.com/ttklon/ZS-MUSIC-MAKER/releases>
- последняя Electron-сборка: <https://github.com/ttklon/ZS-MUSIC-MAKER/releases/latest>
- прямой файл: `https://github.com/ttklon/ZS-MUSIC-MAKER/releases/latest/download/ZS-Music-Maker-Setup-1.0.0.exe`
  (portable — `ZS-Music-Maker-1.0.0-portable.exe`). Имена без пробелов — чтобы
  ссылка вставлялась в чат и не ломалась на `%20`

Тег релиза — `desktop-v<версия>`, поэтому ссылка `releases/latest`
остаётся рабочей от сборки к сборке. Сборку публикует job
`publish-release` после каждой успешной Windows-сборки: артефакты CI для
этого не годятся — они живут 30 дней и открываются только после входа в
GitHub.

Опубликованный релиз (проверено 2026-11-08):
[`desktop-v1.0.0`](https://github.com/ttklon/ZS-MUSIC-MAKER/releases/tag/desktop-v1.0.0) —
`ZS-Music-Maker-Setup-1.0.0.exe` (82 718 855 Б) и
`ZS-Music-Maker-1.0.0-portable.exe` (82 425 858 Б); обе ссылки
`releases/latest/download/…` отвечают 302 на файл.

Если релиза ещё нет, установщик можно взять из артефактов: `Actions → Build
Windows EXE → нужный запуск → ZS-Music-Maker-Windows-Setup`. Python не нужен: бит считается внутри приложения. Раздел «Запуск»
(пайплайн на Python) при его отсутствии честно отключается и говорит об этом
в «Диагностике».

Сборка проверена на `windows-latest`: 2026-11-08 прогон
[42473483401](https://github.com/ttklon/ZS-MUSIC-MAKER/actions/runs/42473483401)
собрал NSIS-установщик и portable EXE (~165 МБ артефакта), запустил
упакованное приложение с `--smoke` — все проверки прошли: корень проекта
`resources/project`, 120 жанров, 299 модулей, `REAL_PASS` банка, рендер
2-секундного бита.

Windows 11, из исходников:

```powershell
cd desktop
npm install            # electron + electron-builder
npm start              # окно
npm run dev            # окно + DevTools
npm run dist           # установщик NSIS и portable EXE в desktop/dist
```

`npm run dist:dir` собирает распакованный каталог — его быстрее проверять, в
том числе через `--smoke` (см. ниже).

### Сборка для Windows

`package.json → build` — единственное место, где описан состав сборки:

- `data/samples/`, `data/desktop/`, `data/genre_presets/`,
  `data/artist_dossier/`, `config/genres_100.json` и `version.json`
  попадают в `resources/project` — приложение читает их как корень проекта
  (`electron/runtime.js`);
- `electron/**` распакован (`asarUnpack`): файл потока рендера нельзя
  открыть из `app.asar`;
- NSIS: установка «для пользователя» (без прав администратора), выбор
  каталога, ярлыки на рабочем столе и в меню «Пуск»;
- portable EXE — тот же код без установки.

### Окно на Windows 11

То, что отличает приложение от «окна браузера» на Windows, живёт в
`electron/window-policy.js` и `electron/app-menu.js` — там же, где его
проверяют тесты (`test/window-policy.test.js`), потому что `electron` в этих
модулях не требуется:

- `app.setAppUserModelId('ru.zsmm.musicmaker')` — тот же идентификатор, что
  `build.appId`. Ставится только у собранного приложения: иначе ярлык и
  окно оказываются в разных группах панели задач, а иконка берётся чужая;
- `requestSingleInstanceLock()` берётся до `whenReady`. Второй запуск не
  поднимает второй процесс, а разворачивает (`restore`), показывает
  (`show`) или фокусирует уже открытое окно — иначе два экземпляра писали бы
  один `settings.json` и один файл банка;
- закрытие всех окон завершает процесс (кроме macOS, где так принято), а
  вместе с ним останавливается запущенная Python-задача;
- меню своё: в сборке нет «Перезагрузить» и «Инструменты» — они сбрасывали
  собранный бит. «О приложении» показывает версию проекта, корень данных и
  версии Electron/Node/Chromium;
- заголовок окна — `ZS Music Maker v<версия>`, чтобы в списке задач было
  видно, какая сборка открыта;
- если окно упало или перестало отвечать, приложение объясняет это и
  предлагает перезагрузить. При нехватке памяти (`oom`) перезагрузка не
  предлагается: она повторит ту же ошибку;
- индикатор на кнопке панели задач: во время рендера бита — проценты, во
  время задачи «Запуск» — бесконечный, пока процесс жив. Свёрнутое окно
  иначе выглядит зависшим;
- размер окна запоминается в `settings.json` и восстанавливается при
  следующем запуске. Развёрнутое, свёрнутое и полноэкранное окно не
  запоминается: после перезапуска оно открылось бы «во весь экран» без
  кнопки «развернуть».

### Где приложение хранит досье

Из репозитория (`npm start`) досье читается и пишется в
`data/artist_dossier` проекта. В установленной сборке так нельзя: данные
лежат в `C:\Program Files\ZS Music Maker\resources\project`, а этот каталог
обычному пользователю недоступен для записи. Поэтому `electron/writable-data.js`
выбирает каталог:

| Запуск | Куда пишется досье |
|---|---|
| `npm start` из репозитория | `data/artist_dossier` проекта |
| установленное приложение | `%APPDATA%\zs-music-maker-desktop\artist_dossier` |

При первом запуске установленной сборки туда один раз копируются
`schema.json` и `demo_artist/artist.json`; маркер `.seeded.json` не даёт
вернуть демо-артиста, если пользователь его удалил. Раздел «Диагностика»
показывает фактический каталог и причину выбора.

### Задачи, которые работают без Python

Раздел «Запуск» не целиком зависит от Python: три задачи считает сам главный
процесс (`electron/native-tasks.js`), и они работают в установленном
приложении, где интерпретатора нет.

| Задача | Что проверяет |
|---|---|
| Проверка файлов проекта | `version.json`, каталог жанров (≥ 100), `data/samples/manifest.json`, снимок `inventory.md`, каталоги пресетов и досье |
| Готовность: снимок против пересчёта | пересчитывает готовность окном и сверяет со снимком; расхождение — это ошибка, а не «нюанс» |
| Сводка по досье | артисты, треки, сколько ждёт разбора; отсутствие `tracks/` не считается поломкой |

Вывод построчный: `OK …` либо `ПРОБЛЕМА …`, последняя строка — итог. Задачи,
которым нужен Python (полный прогон, сборка досье, смоук), остаются на месте и
помечены подписью «Python не найден» — но только когда выбрана такая задача.

Проверка сборки без человека: `ZS Music Maker.exe --smoke` открывает проект,
читает версию, каталог жанров, inventory, снимок готовности, банк сэмплов,
собирает двухсекундный бит, рендерит тестовый дубль вокала в микс (с
обязательной пометкой «не с микрофона»), проверяет каталог досье для записи,
запускает задачу «проверка файлов» без Python, читает досье и
добавляет-удаляет артиста с треком во временном каталоге, затем печатает JSON
в `ZSMM_SMOKE_OUT` и выходит с кодом 0/1. Всего 13 проверок; записывать в поставку smoke не
пытается (`resources` может быть только для чтения). Это делает job
`desktop-windows` в CI на `windows-latest`.

Python нужен только для раздела «Запуск» и для обновления снимка чисел:

```bash
export ZSMM_PYTHON=/путь/к/python3      # если интерпретатор не в .venv
npm run snapshot                         # обновить data/desktop/*.json|md
```

## Бит собирается внутри окна

Раздел «Бит» рендерит трек в главном процессе (`zsmm:beat-render`) и отдаёт
окну готовый WAV в base64: страница ничего не считает и не получает `fs`.
Тот же движок крутится в `npm run preview`, поэтому предпросмотр в браузере
не «рисует заглушку».

Что уже перенесено из Python (`modules/beat/`, 2779 строк):

## Вокал: три источника, один честный отчёт

Голос миксуется в трек **до** мастеринга (`engine.js::mixVocal`), поэтому он
часть песни, а не украшение поверх готового файла. Источник выбирается в
разделе «Бит»:

| Режим | Что это | `source` | `simulated` |
|---|---|---|---|
| без вокала | трек без голоса | — | — |
| синтез голоса | формантный синтез `vocal.js` по тексту строки | `synth` | `false` |
| тестовый дубль | имитация входа записи для проверки цепочки | `test` | `true` |
| WAV-файл | своя запись, выбранная в системном диалоге | `file` | `false` |

Правила, которые держат тесты (`test/takes.test.js`, `test/vocal-mix.test.js`):

- тестовый дубль **не может** выдать себя за запись: `assertHonest` падает,
  если `source: 'test'` пришёл без `simulated: true`, а в интерфейсе он
  подписан «тестовый дубль (не с микрофона)»;
- захвата с микрофона в приложении нет (нужен native-модуль), и окно так и
  пишет: `zsmm:vocal-input` отвечает `recording: false` с причиной;
- параметры проверяются до рендера: неизвестный режим, путь без `.wav`, `..`
  в пути, уровень вне 0…1 — отказ с текстом, а не молчаливый ноль;
- вокал длиннее трека обрезается, и в отчёте стоит `starts_outside: true`;
- готовый мастер открывается в системном плеере (`zsmm:beat-open-external`),
  а дубль сохраняется отдельным WAV (`zsmm:vocal-export`) — ровно тот, что
  попал в микс, а не «примерно такой»;
- мелодия строится по тональности трека (`melodyFor`) и держится в диапазоне
  MIDI 55…74: ниже голос «бубнит», выше свистит на согласных.

`takes.js` — чистая логика: он ничего не пишет на диск. Файл вокала читает
главный процесс (`beat-service.js`), в поток уходит уже готовый дубль.

## Досье ведётся из окна

Пустой раздел «Досье» раньше отправлял в терминал. Теперь артист
добавляется кнопкой: окно пишет `data/artist_dossier/<slug>/artist.json` в
том же формате, что `modules/artist_dossier/schema.py` (поля `artist`,
`slug`, `tracks`, `dossier`, `added_at`, `updated_at`), и удаляет каталог
артиста, не выходя за пределы `data/artist_dossier` (проверка — по
разрешённому пути, не по строке из окна). Раздел «Треки» заводит трек без
Python: название, ссылка и текст сохраняются как
`tracks/<id>.json` (и `lyrics/<id>.txt`), идентификатор считается по той же
формуле, что `schema.py::_track_id`. Статус записи — `pending` («не
разобран»): темп, тональность и разбор вокала заполняет Python, и окно их не
выдумывает. Полная сборка досье (биография, темы, анализ треков) по-прежнему
требует Python — это написано в подписи раздела. Запись, созданная окном,
читается менеджером: `note` — поле записи, а лишние поля не роняют чтение
(раньше один такой файл ломал список всех артистов).
В поставке лежит `demo_artist`, помеченный как `[демо из поставки]`, чтобы
раздел не выглядел сломанным на первом запуске.

Проверки, которые держат совпадение с Python:

- `node --test test/patterns.test.js` — ритм и акценты по всем семействам;
- `node --test test/dsp.test.js` — АЧХ фильтров против чисел из scipy;
- `node --test test/engine.test.js` — 20 с бита, пик ≤ 0.98, тот же seed →
  тот же WAV, куплет тише хука;
- `pytest tests/test_desktop_audio_port.py` — таблицы JS против
  `modules/beat/patterns.py`, проекция 120 жанров, WAV читается `soundfile`.

### Сэмпловый банк подключён

Окно читает `data/samples/manifest.json` и сами one-shot'ы с диска: 32 файла,
6 барабанных инструментов (кик, снейр, клэп, хэт, открытый хэт, 808).
Разрешены только CC0/CC-BY/public-domain — остальное помечается и в трек не
попадает. Поэтому статус движка в приложении — **`REAL_PASS`**
(`sample_bank+procedural`), как у Python с тем же банком; при выключенном
банке он честно падает в `FALLBACK`.

Отличий от Python два, и оба измерены:

* **Выбор one-shot'а не совпадает.** Python берёт сэмпл из `_np_rng`, который
  он же использует для шума синтеза; в окне это отдельный поток
  (`noiseRng`), чтобы выбор сэмпла не сдвигал «человечность». Тот же seed даёт
  тот же трек внутри окна, но не тот же файл, что Python, — поэтому сравнение
  с эталоном идёт по полосам спектра (тело и верх ≤ 3 дБ, низ ≤ 6 дБ), а не
  по сэмплам.
* **SHA-256 не пересчитывается на каждый удар.** Это чтение всего файла;
  проверка целостности вынесена в `bank.verifyChecksums()` и в тесты.

### Замеры совпадения с Python

| Что сравнивается | Как | Результат |
|---|---|---|
| Синтез без банка, секции intro/verse/hook | 8 полос спектра | расхождение **≤ 1.7 дБ** |
| С банком, секция hook | те же полосы | тело и верх **≤ 3 дБ**, низ ≤ 6 дБ |
| Гейны банка (`BANK_GAIN`) | числа против `drums.py` | совпадают |
| Статус и покрытие банка | против `samples.capability()` | совпадают |
| Таблицы ритма и акцентов | против `patterns.py` | совпадают |
| «Формульность» (`repetition_report`) | энтропия/сходство на клик-треке и бите | 0.650 против 0.641 у Python |
| «Человечность» микса | шумовой пол и вариативность | −36.9 против −37.9 dBFS |
| Пошаговый рендер против синхронного | побайтовое сравнение WAV | совпадают |

Замер скорости: 20 секунд бита (140 BPM, phonk, seed 7) — **≈1.5 с** в Node
против ≈1.0 с в Python. Разница — отсутствие numpy, а не другой алгоритм.

## Чего здесь нет (честно)

- **Графическое окно здесь не запускалось.** В этой среде нет
  `Xvfb`/`libgtk`/`libnss3`, поэтому Electron не стартует. Проверены:
  синтаксис всех файлов, логика (`core/*`, `runtime.js`, `pipeline.js`,
  `beat-service.js`, `settings.js`) на настоящих данных, рендер всех скриптов
  окна в DOM-двойнике (`test/fake-dom.js`), контракт `index.html` ↔
  `app.js`/`sections/*` ↔ `preload.js`. Проверка на настоящей Windows
  проходит в job `desktop-windows`: сборка NSIS плюс запуск упакованного
  приложения с `--smoke` — прогон 42473483401 зелёный. Чего это не
  доказывает: что окно **визуально** выглядит правильно — его никто не
  открывал глазами, проверены данные и контракт разметки.
- **Установщик собирается только в CI.** В среде разработки агента нет
  Windows и скачивания Electron, поэтому артефакты лежат в CI
  (`ZS-Music-Maker-Windows-Setup`), а не в репозитории.
- **Подписи кода нет.** Установщик не подписан сертификатом: Windows 11
  покажет предупреждение SmartScreen при первом запуске. Метаданные EXE при
  этом заполняются: `signAndEditExecutable` больше не выключен, поэтому в
  свойствах файла есть версия и описание. Это проверяется тестом
  `test/packaging.test.js` — раньше один флаг отключал и подпись, и правку
  ресурсов, и файл выглядел безымянным.
- **Выбор сэмпла не совпадает с Python такт в такт.** Причина описана выше:
  в Python один RNG на шум и на выбор сэмпла, в окне — два потока. Внутри
  окна детерминизм полный (`seed` → тот же WAV), между окном и Python —
  совпадение характера, а не файла.
- **Отмена полностью не мгновенная.** Кнопка «Отменить» в разделе «Бит»
  прерывает рендер между секциями: сигнал доходит до движка, воркер выходит
  сам, окно показывает «Рендер отменён — бит не сохранён» без ошибки.
  Посреди одной секции (самая длинная — мастеринг) отмена ждёт её конца, то
  есть до нескольких секунд. Незавершённый WAV на диск не попадает: файл
  пишется только после успешного рендера.
- **Рендер идёт в отдельном потоке, но не в отдельном процессе.** 3 минуты
  бита считаются в `worker_threads`: окно живо и получает прогресс. Общий
  с главным процессом поток ОС при этом загружен, поэтому на слабых машинах
  возможны просадки анимаций; отдельный процесс (`utilityProcess`) не сделан.
- **Записи с микрофона нет.** Захват звука со входа требует отдельного
  native-модуля (PortAudio/WASAPI), его в поставке нет; в Linux-сборке и в
  CI микрофона физически нет. Доступные пути — WAV-файл и тестовый дубль,
  который честно помечен как имитация. Синтез голоса (`vocal.js`) — не
  вокалист и не клон голоса: это разборчивая мелодия с формантами.
- **Раздел «Запуск» требует Python.** Рендер бита, каталог жанров, досье
  (добавление и удаление) и готовность работают без него; полная сборка
  досье и пайплайн `python main.py …` — нет. В
  установленном приложении Python не поставляется, и «Диагностика» говорит
  об этом прямо, вместо того чтобы показывать пустой вывод.
