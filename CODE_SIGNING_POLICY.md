# Политика подписи кода

Этот документ описывает, как подписываются сборки ZS Music Maker и что делать,
пока подписи нет. Он написан по требованиям SignPath Foundation к открытым
проектам (бесплатная подпись для OSS) и годится как основа для заявки туда же
или для настройки Azure Trusted Signing.

**Текущее состояние: подписи нет.** Ни один EXE из релиза
`desktop-v1.0.0` не подписан, поэтому Windows 11 показывает предупреждение
SmartScreen при первом запуске. Это ограничение сертификата, а не сборки:
сборка, тесты и smoke-проверка проходят.

## Что именно подписывается

| Артефакт | Подписывается | Кем |
| --- | --- | --- |
| `ZS-Music-Maker-Setup-<версия>.exe` (NSIS) | да, на этапе `electron-builder` | сертификат издателя |
| `ZS-Music-Maker-<версия>-portable.exe` | да, на этапе `electron-builder` | тот же сертификат |
| `ZS Music Maker.exe` внутри установщика | да, до упаковки в NSIS | тот же сертификат |
| `smoke.json`, `signature.json` | нет (это отчёты, а не исполняемые файлы) | — |

Проверка подписи — отдельный шаг сборки: `desktop/scripts/verify-signature.js`
спрашивает у Windows (`Get-AuthenticodeSignature`) и пишет `signature.json`,
который едет в артефакты и в релиз. В тексте релиза не утверждается
«подписано»: там только ссылка на отчёт.

## Вариант A. SignPath Foundation (бесплатно для OSS)

Условия и порядок (по публичной документации SignPath; окончательное решение
принимает фонд, а не проект):

1. Заявка на <https://signpath.org/>: описание проекта, ссылка на репозиторий,
   лицензия, кто и что выпускает. Рассматривают вручную, это недели.
2. Проект должен быть открытым и **заметным**: у фонда есть отказы проектам без
   внешних ссылок и трафика. Наш репозиторий пока не публичный по существу, и
   это единственное настоящее препятствие.
3. Нужен опубликованный документ о политике подписи — этот файл, доступный по
   постоянной ссылке, с указанием ролей и приватности (разделы ниже).
4. После одобрения выдаются `SIGNPATH_API_TOKEN`, `SIGNPATH_ORGANIZATION_ID`,
   `SIGNPATH_PROJECT_SLUG`, `SIGNPATH_SIGNING_POLICY_SLUG`. В GitHub Actions
   добавляется шаг `signpath/github-action-submit-signing-request` (пиннить по
   SHA, не по тегу).
5. Каждый релиз одобряется вручную в панели SignPath — это не «включил и
   забыл». Подписывается **готовый .exe**: внутрь NSIS-установщика подпись не
   залезает, поэтому подписывать нужно и установщик, и portable-сборку, и
   распакованный `ZS Music Maker.exe` до упаковки.

## Вариант B. Azure Trusted Signing

Платно (порядка 10 $/мес за базовый уровень), зато без модерации фонда.
Требуется проверка личности (документ) и три значения из портала Azure плюс
три секрета Entra ID. Настройка в репозитории уже готова:

```
AZURE_CODE_SIGNING_ENDPOINT      # https://<регион>.codesigning.azure.net
AZURE_CODE_SIGNING_ACCOUNT_NAME  # имя аккаунта Trusted Signing
AZURE_CERTIFICATE_PROFILE_NAME   # имя профиля сертификата
AZURE_CLIENT_ID                  # service principal с ролью
AZURE_TENANT_ID                  #  «Trusted Signing Certificate Profile Signer»
AZURE_CLIENT_SECRET
```

Если все шесть заведены в Secrets репозитория, `desktop/scripts/build-config.js`
добавляет в конфигурацию `win.azureSignOptions`, и `electron-builder` подписывает
файлы через `Invoke-TrustedSigning` с меткой времени `http://timestamp.acs.microsoft.com`.
Если хотя бы одного значения нет — блока подписи нет вовсе, сборка выходит без
подписи и не падает.

## Вариант C. Свой сертификат

Обычный код-сигнинг сертификат (OV/EV) от любого CA: подпись через
`signtool.exe`, настройка в `win.signtoolOptions`. Секреты — в GitHub Secrets,
никогда в репозитории.

## Роли

| Роль | Кто | Что делает |
| --- | --- | --- |
| Владелец проекта | `@ttklon` | принимает решения о выпуске, заводит секреты, одобряет заявки на подпись |
| Сборка | GitHub Actions (`Build Windows EXE`) | собирает артефакты, подписывает (если настроено), проверяет подпись, публикует релиз |
| Проверка | `desktop/scripts/verify-signature.js` | независимо от сборки спрашивает у Windows, подписан ли файл |

Ни у одной роли нет доступа к приватному ключу в открытом виде: ключ живёт в
сервисе подписи (SignPath или Azure), а в репозиторий попадает только токен.

## Приватность и данные

- Подпись ничего не отправляет о пользователе: подписываются только файлы
  сборки, применённые к публичному коду репозитория.
- Внешним сервисам (SignPath, Azure) передаются исполняемые файлы релиза и
  метаданные проекта (имя, версия). Кода пользователей и их данных там нет.
- Само приложение работает без сети: оно не собирает и не отправляет данные,
  подпись на это не влияет.

## Как проверить подпись самому

```
# на Windows 11, в PowerShell
Get-AuthenticodeSignature '.\ZS-Music-Maker-Setup-1.0.0.exe' | Format-List

# или скриптом из репозитория
node desktop/scripts/verify-signature.js .\ZS-Music-Maker-Setup-1.0.0.exe
```

Коды возврата: `0` — подпись действительна, `1` — не подписано или подпись
битая, `2` — проверить нечем (не Windows). «Не проверили» никогда не
считается «подписано».

## Пока подписи нет

- В README, «Справке» приложения и в тексте релиза это сказано прямо.
- Первый запуск на Windows 11 показывает SmartScreen: «Windows защитила ваш
  компьютер». Это ожидаемо; кнопка «Подробнее» → «Выполнить в любом случае».
- SHA-256 файлов релиза можно сверить с тем, что пишет CI (`Show what was
  built` в логе сборки), но это не заменяет подпись: хеш в логе может
  подделать тот, кто подделает лог.
