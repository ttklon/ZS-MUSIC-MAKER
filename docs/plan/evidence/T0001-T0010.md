# Пакет 001 — единая спецификация продукта

## Объём

T0001–T0010 относятся к спецификации и согласованности поставки, справки и
документации. Они НЕ закрывают сценарии генерации, singing backend, чистую NSIS
установку и hardware acceptance. Для них остаются отдельные задачи плана.

## T0001 — входной контракт

Канонический источник: `desktop/src/core/product-contract.js`, schema 1,
`zsmm-windows-studio`. Документ: `docs/PRODUCT.md`. Версия берётся из version.json,
а не дублируется в контракте. Целевой основной вход: Electron → Создание трека,
Windows 11 x64, NSIS per-user. Четыре обязательных сценария имеют accepted=false
и явные причины. Входы/ожидаемые результаты приведены в спецификации.

## T0002 — воспроизведение baseline

Baseline `39f8a85c1c2db9eef5a22aff023695b096813dae`:

- `git show 39f8a85:desktop/src/sections/help.js` содержит «Сеть не используется
  вовсе» и «Установщик ... не main.py, app/ и modules/».
- `desktop/package.json` и release workflow поставляют Python-код/встроенный Python;
  `app/core/bootstrap.py` готовит backend с сетевым согласием. Это противоречие
  описания поставки, не утверждение успешного inference.
- README начинал инструкции с setup.cmd/run_silent.cmd для legacy PySide, тогда как
  основное окно — Electron. Архивы прежних README сохранены в `docs/history/`.

Воспроизвести: прочитать указанные версии через git show и сравнить с extraResources
в package.json и шагом Bundle Python в release.yml. Данные пользователя не нужны.

## T0003 — решение

Один статический контракт, доступный и Node-тестам, и renderer. Не новый IPC,
не сетевой запрос и не ещё одна настройка. Из него генерируются docs/PRODUCT.md
и блок README; справка читает тот же объект. Runtime-проверка возможностей не
подменяется контрактом. Альтернативы: независимые тексты (снова разойдутся),
fetch JSON (не нужен при CSP connect-src none), новый IPC (лишняя поверхность).
Откат: revert соответствующего commit, не затрагивая projects/models/settings.

## T0004 — реализация

`core/product-contract.js`, `scripts/product-spec.js`: проверка productName,
версии, x64 NSIS, per-user и имени asset. Генератор --check только читает;
рассогласование завершает процесс с ошибкой, не переписывает документацию.

## T0005 — интеграция

index.html загружает контракт до help.js. Справка строит карту сценариев из
контракта, показывает границы подтверждения и устранение сбоя. Удалены устаревшие
утверждения об отсутствии Python-кода и о полном отсутствии сети. README описывает
тот же Electron-продукт; старые команды сохранены как исторические, не основной путь.

## T0006 — отказы

При отсутствующем/неподдержанном контракте справка показывает «Спецификация
недоступна», не оптимистичный список функций. Несовпадение версии/имени installer
останавливает metadata check. Негативные тесты работают с временной копией,
подтверждают отсутствие изменения входных файлов. Пользовательские данные и веса
не затрагиваются. Совет восстановления: экспорт ошибки, не удаление данных/pip.

## T0007 — регрессия

`desktop/test/product-contract.test.js`: метаданные, одинаковый browser/Node
контракт, отрицательные проверки версий/asset, актуальность документации.
`render.test.js` и `ui-contract.test.js`: реальный DOM-код с тестовым мостом;
это не packaged test. Локальный запуск 42 тестов завершился без ошибок.

## T0008 — Windows

Workflow `Product plan integrity - Windows`, job `packaged-product-specification`:
Node contract/DOM tests → npm build tools → electron-builder dir → реальный EXE
с --window-check. Проверяется переход help и data-product-id в загруженном окне.
Это упакованная development-сборка без публикации; не тест чистой NSIS установки
или встроенного Python. Ссылка и фактический результат добавляются после job.

## T0009 — предметная приёмка

Принимается только совпадение имени/версии/установщика, платформы, сценариев и
ограничений в контракте, документации и упакованной справке. Должны пройти
позитивный и негативный тесты. Принятие спецификации не меняет accepted=false
у сценариев песни и не повышает продуктовую готовность.

## T0010 — сопровождение

Правила обновления указаны в desktop/README.md. Источник меняется первым,
`node desktop/scripts/product-spec.js` обновляет документы, --check контролирует
дрейф. Windows workflow запускается при изменениях источника/справки/спецификации.
План и PROJECT_STATE обновляются после сохранения результата Windows-проверки.

## Итоговая проверка

Ожидается Windows job; до её результата пакет не считается verified.
